Strengths to keep

What is already enterprise-strength

These are design choices a buyer's architects will like:

Evidence, not opinion

Twin runs are graded on traces and labelled outcomes. Pass rates carry confidence ranges, and versions are compared with paired tests.

Reproducible

Every run snapshots the agent, environment, dataset, model and policy versions. Batch cases are seeded and replayable.

Governed agents

Permissions, tool contracts, guardrails, escalation and model policy are part of the agent definition, and the twin's tool gateway enforces them.

Context-aware

The organization's policies, roles and approval limits ground every blueprint and agent, with citations.

Safe by default in test

API mode only calls non-production endpoints. Sample-data systems need no live systems at all.

Whole-process proof

The process twin runs every agent over many cases and prices the result against today's operating model.

The bar

What an enterprise buyer will ask for

Eight areas, roughly in the order a security review and a pilot will probe them:

Identity and access

SSO, MFA, SCIM, fine-grained roles, segregation of duties between who builds, tests and approves an agent.

Tenancy and data

Hard isolation between customers and units, encryption with customer-managed keys, residency, retention.

Security and compliance

SOC 2 Type II, ISO 27001, GDPR, EU AI Act evidence; in banking also DORA and outsourcing rules.

Reliability and scale

SLA, DR, horizontal scale, thousands of concurrent twin cases, predictable cost.

Operability

Metrics, tracing, alerting, audit logs, admin consoles, zero-downtime deploys.

Production agent runtime

Agents that actually run, with identity, kill switch, monitoring and drift checks against the twin.

The critical four

Four gaps block any enterprise deployment

Identity, tenancy, a production runtime, and data protection. Everything else can follow a pilot.

6 / 21
1 · Identity

From 'type your name' to real identity and roles

Today

  • Login takes a name and a role the user picks: anyone who reaches the API can be an Editor
  • Two roles: viewer and editor
  • 30-day cookie sessions; no revocation beyond logout
  • No link to the customer's directory

Enterprise grade

  • OIDC/SAML SSO with the customer's IdP; MFA enforced there
  • SCIM provisioning; groups mapped to roles
  • Roles that match the work: analyst, architect, process owner, approver, auditor, admin
  • Segregation of duties: whoever builds an agent can't approve its release
  • Short sessions, refresh tokens, admin revocation

Effort: about 6-8 engineer-weeks, including the role model and UI gating.

7 / 21
2 · Tenancy

From one organization to many, isolated

Today

  • The organization is a singleton; no table carries a tenant id
  • A second customer means a second deployment
  • Business-unit stewardship exists, but only within one organization

Enterprise grade

  • tenant_id on every row, enforced by Postgres row-level security, not just by queries
  • Per-tenant encryption keys, model policy, budgets and rate limits
  • Optional dedicated deployments (single-tenant, in-region) from the same build
  • Tenant-scoped exports and deletion, for GDPR and contract exit

Effort: about 8-10 engineer-weeks. Touches all 49 tables and every repository query, so do it before more features land.

8 / 21
3 · Production agent runtime

From proven in the twin to running for real

Today

  • The twin is the only place an agent runs
  • 'DEPLOYED' means published to a registry entry
  • No agent identity, credentials or production tool adapters
  • No production monitoring, so no way to compare live behaviour with the twin

Enterprise grade

  • A runtime that reuses the twin's tool gateway, guardrails and checkpoint model, so tested is what runs
  • Workload identity per agent, with scoped, short-lived credentials to each system
  • A human-review inbox for real checkpoints, with SLAs and escalation
  • Kill switch, canary rollout, live metrics, and drift alerts against the twin baseline
  • Or a certified hand-off to the customer's agent platform (MCP / A2A)

Effort: the largest single item, about 4-6 months for a team of 3-4. It's where customer value is realised.

9 / 21
4 · Data protection

From local files to a defensible data posture

Today

  • API keys in backend/.env
  • Uploads, usage and app logs unencrypted on the container disk
  • Policy text and case data go to a third-party model gateway by default
  • PII redaction by regular expression

Enterprise grade

  • Secrets manager (Vault, Key Vault, Secrets Manager); no secrets in images or env files
  • Object storage with KMS and customer-managed keys; retention policies
  • Default-deny model policy: EU-hosted or private models unless allowed
  • DLP-grade redaction or tokenisation before any model call; full model-call audit log
  • DPIA and records of processing ready for customers' data protection officers

Effort: about 6-8 engineer-weeks, plus the policy work for the DPIA.

Engineering plan

Refactor the hot core while the product is still young

Split the repository

Per-domain stores (process, agent, twin, context, datasets) and services; orchestration out of the persistence layer.

A walk engine

The orchestrator's graph walk as a small state machine with parallel gateways, timers and resumable steps, replacing nested closures.

Remove hidden cycles

Jobs register through entry points, not by importing the app; package boundaries checked in CI.

CI with gates

Tests, type checks (mypy/pyright), lint, code-health ratchet, docs check and dependency audit on every change.

Contract tests

Pydantic schemas versioned for the JSON columns, with migrations that rewrite old payloads.

Frontend structure

A query cache instead of per-page polling; split the large panels; end-to-end tests of the main journeys.

Roadmap

Twelve months to enterprise grade

Phases overlap. Each ends in something a customer can use.

Phase 0 · Safe to pilot

Weeks 0-6
  • OIDC SSO and real roles
  • Secrets manager, object storage, encryption at rest
  • CI with tests and the code-health and docs gates
  • Worker split from the API; append-only run steps

Phase 1 · Multi-tenant platform

Months 2-5
  • tenant_id and row-level security
  • Kubernetes/Helm, autoscaled API and workers
  • OpenTelemetry, alerts, audit log
  • LLM gateway with failover and budgets
  • Pen test; SOC 2 controls start

Phase 2 · Agents in production

Months 4-8
  • Agent runtime reusing the twin's gateway
  • Agent identity and scoped credentials
  • Human-review inbox; kill switch; canary
  • Live monitoring and drift against the twin

Phase 3 · Certified and at scale

Months 6-12
  • SOC 2 Type II, ISO 27001
  • DR drills; in-region deployments; customer-managed keys
  • Refactor complete: repository split, walk engine
  • Parallel gateways and capacity simulation in the twin

Decisions needed

Four decisions to make now

These shape the plan more than any engineering choice:

  • Deployment model: multi-tenant SaaS, dedicated single-tenant, or both from day one?
  • Runtime strategy: run agents ourselves, hand them to customer platforms, or both?
  • Model strategy: which providers and regions to support for regulated customers (EU-hosted, private)?
  • First certified market: banking (DORA, outsourcing rules) or broader enterprise (SOC 2 first)?
